## Current invariant or soft constraint

A01-A15 remain authoritative. In particular, A01-A03 require event-driven
logical execution, local elapsed time and finite propagation; A04 and A08
require bounded topology and dynamics; A06-A07 preserve predictive coding,
explicit error events and local learning; A09-A11 separate local resource
accounting from usefulness and allow delayed credit; A14 requires bounded local
structural adaptation; and A15 requires hardware-independent semantics.

ACP-0002 N2 is closed and remains authoritative for static Model-B edge
transfer and canonical neuron integration:

```text
z_ij = tanh(w_ij * a_i)
v_ij = d_ij * z_ij + (1 - d_ij) * r_ij
s_j(t_k+) = clip(s_j(t_k-) + v_ij)
a_j = tanh(g_j * s_j)
```

Elapsed-time decay is applied before arrival integration. Equal-time fan-in is
canonical deterministic sequential processing; downstream work may occur
between equal-time arrivals. This ACP references those semantics and does not
redefine them. It also does not authorize edge learning, ACP-0002 N3, Luna-13F
reopening or Luna-13G.

## Observed problem

**OBSERVED:** The architecture must eventually support GPU, FPGA and FPAA
realizations, while the current software reference is the most concrete
execution description.

**INFERRED:** Without an explicit separation, GPU batching, floating-point
arithmetic, software queues or host instrumentation could become accidental
architectural requirements. Conversely, prematurely embedding FPGA register
layouts or FPAA calibration values in logical state would make the reference
model device-specific.

**HYPOTHESIZED:** A canonical execution representation plus declared backend
approximation contracts will permit efficient device implementations while
making semantic loss observable and classifiable.

## Proposed change

The architecture boundary is:

```text
canonical TPCN semantics
    -> device approximation contract
        -> device implementation
```

Canonical semantics define what the logical network computes. A backend
contract declares required equivalence classes, timing/precision/resource
approximations and unsupported behavior. A device mapping determines how the
contract is realized. No backend may promote its convenient numerical model,
clock, memory layout or instrumentation format into canonical semantics.

### Canonical TPCN Execution IR

Define a future hardware-neutral IR at the interface boundary. This ACP
approves the concept and schema direction only; it does not implement it.

Logical records should represent:

```text
Edge:
    source, destination, edge_weight, divider_strength, reference,
    propagation_delay
Neuron:
    id, decay_rate, state_limit, neuron_gain, activation_model
Event:
    event_id, source, destination, timestamp, payload, event_type
```

Future bounded neuron fields may include accumulator limits, thresholds,
reset mode and attractor mode. They are optional future schema extensions and
do not authorize the proposed attractor neuron.

The IR must encode logical state, finite bounds, reset boundaries and event
identity without CUDA dimensions, FPGA register addresses/RTL names, FPAA
channel or op-amp identifiers, DAC assignments or PCB routes. Device mappings,
quantizers, lookup-table addresses, calibration coefficients and physical
control values remain outside the IR. Serialization must preserve declared
logical ordering and version the schema; it must not imply that every backend
can reproduce every internal state bit exactly.

The following ownership boundary is normative for review and staging:

| Responsibility | Canonical requirement | Placement guidance |

| Event identity and ordering | Yes where logical events are represented | GPU/FPGA primary; FPAA interface or hybrid control |
| Scheduling, queues and finite delay | Yes; no global neural tick | GPU/FPGA primary; FPAA timing interface or hybrid |
| Local time and elapsed decay | Yes | All backends, with analog continuous-time mapping declared |
| Neuron accumulation/nonlinearity | Yes within declared model | All backends; device approximation must be declared |
| Threshold/spike/attractor logic | Only when a future neuron model authorizes it | GPU/FPGA/FPAA capable; not activated here |
| Prediction and error events | Yes | Local backend components or hybrid control, preserving causality |
| Delayed reward and eligibility | Yes where enabled | Bounded digital control is likely; FPAA mapping remains research |
| Structural plasticity | A14 capability, optional per milestone | Bounded digital/control layer likely; no placement is approved |
| Edge learning | Not authorized by this ACP | No backend may activate it |
| Instrumentation/visualization | Downstream-only | GPU/FPGA export/control; never a semantic input |
| Serialization/state transfer | Canonical logical state boundary | Backend adapters add realization state separately |

### GPU native contract

GPU native is the high-precision/reference research implementation. It may
support large simulation, training, instrumentation, visualization and artifact
generation. It must preserve event causality, local timestamps, finite delays,
bounds and deterministic declared ordering. Floating point, CUDA batching and
parallel kernels are realization choices. A batch is never a neural timestep,
and GPU behavior does not define canonical requirements merely because it is
convenient.

### GPU FPGA approximation contract

This is an emulation of expected FPGA numerical and resource constraints, not
an FPGA implementation. A mode may model fixed-point fields, saturating
arithmetic, LUT or polynomial transfer approximations, finite timestamp and
queue representations, discrete delay resolution, bounded accumulators and
hardware-like deterministic arbitration. Exact widths, quantizers and LUTs are
not frozen by this ACP. Each run must declare them and compare against GPU
native using predeclared numerical, event, structural and resource criteria.

### FPGA native contract

An eventual FPGA backend may own finite event queues, event identity, routing,
local-time metadata, deterministic arbitration, finite topology state,
Model-B arithmetic, fixed-point neuron updates, prediction/error bookkeeping,
bounded reward identity/idempotency, eligibility state, structural control and
telemetry/export. These are likely device assignments, not new canonical
semantics. DE1-SoC limits, register maps, pin assignments, clocks and RTL names
must remain mapping details. FPGA clocks may schedule hardware but must not
become a global neural timestep.

### GPU FPAA approximation contract

This mode intentionally models physical dynamical effects rather than merely
reducing numeric precision. It may include declared leaky continuous-time
integration, nonlinear transfer curves, finite rails, reference offsets,
component mismatch, finite slew, threshold variation, noise, relaxation and
future history-dependent effects. The noise and physical model remain
configuration choices until separately reviewed. Statistical or functional
criteria may be more appropriate than trace equality.

### FPAA native contract

An FPAA realization may own edge transfer, local reference behavior,
nonlinear saturation, leaky accumulation, thresholding, attractor/relaxation
dynamics, physical noise and future local adaptive analog state. Large global
event-ID tables, deterministic idempotency tables, complex topology
transactions and large structural candidate tables are not assumed suitable
for native analog implementation. A digital control interface or hybrid layer
may provide these functions. No specific FPAA partition is accepted by this
ACP.

### Hybrid FPGA + FPAA

The proposed pairing of an FPGA event/control fabric with an FPAA dynamical
compute fabric is retained as a **hardware research hypothesis**, not an
approved architecture mapping. A candidate split is FPGA event identity,
routing, logical time, bounded queues, credit and structural control; FPAA
edge transfer, leaky integration, nonlinearity, attractor dynamics and spike
generation. It must first demonstrate interface timing, finite buffering,
conversion effects, simultaneous-arrival behavior, calibration, resource cost
and equivalence evidence. The split must not hide a global tick or move
nonlocal learning into the analog fabric.

## State portability and calibration

A configured/trained network should have one canonical portable logical state:

```text
canonical TPCN state -> GPU mapping | FPGA mapping | FPAA mapping
```

Portable fields include topology, bounded logical edge parameters, normalized
reference, logical positive delay, neuron gain, bounds and any explicitly
versioned logical thresholds. Backend realization state is separate and may
include fixed-point encodings, LUT addresses, analog calibration coefficients,
physical bias voltages, measured leakage constants, mismatch corrections and
conversion settings. A backend must not silently alter canonical logical
parameters during import.

FPAA calibration is a mapping layer, for example
`r_ij -> calibration -> Vref_ij` and `w_ij -> calibration -> conductance/control`.
Calibration adapts a physical realization to the logical state; it does not
redefine the logical network. Calibration version, validity range and residual
error must be serialized with backend state.

## Timing model and equal-time fan-in

Three notions remain distinct: logical/event time, backend scheduling time and
physical wall-clock time. FPAA additionally has continuous physical time.
Logical event time and positive finite propagation define canonical causality.
GPU/FPGA scheduling batches and hardware clocks are not neural time. An analog
mapping must declare how continuous crossings and sampled interface events map
to logical timestamps and finite delays.

N2's equal-time fan-in is sequential and deterministic, with downstream work
allowed between arrivals. Physical simultaneous summation is therefore **not
exact equivalence by default**. ACP-0003 selects **Model C implemented
conceptually through Model B semantics**:

- strict serialization is required as a validation/reference mode for a future
  FPGA+FPAA test harness, but is not required as the permanent physical
  execution strategy;
- an FPAA may use simultaneous/coincident integration as an explicit backend
  approximation, with functional, numerical, event or statistical acceptance
  declared per experiment;
- a backend-declared coincidence window `epsilon_fan_in` may treat arrivals
  satisfying `abs(delta_t) <= epsilon_fan_in` as physically coincident;
- `epsilon_fan_in` is not canonical network state. It belongs to backend
  contract/calibration state and must carry calibration/version metadata;
- downstream emissions between canonical equal-time arrivals may be absent or
  shifted in analog mode and must be reported as approximation differences.

No silent equivalence claim is permitted. The canonical software/reference
mode remains sequential and deterministic.

## Noise, nondeterminism and equivalence classes

The canonical logical execution remains deterministic where required. A noisy
FPAA realization may be stochastic when its contract explicitly declares that
behavior. Equivalence must be selected per observable:

- Functional: same qualitative or categorical behavior.
- Numerical: output within a declared tolerance.
- Event: relevant sequence within timing tolerance.
- Structural: same topology or edge-state decisions where required.
- Statistical: declared distributions or aggregate behavior agree.

Candidate statistical measures include firing probability, timing
 distributions, classification, prediction-error distribution, attractor
 occupancy and event/resource rates. Bitwise equality is not required across
inherently different technologies. Every comparison must state seed, workload,
reset policy, precision/noise/calibration configuration and acceptance bounds.

## Equivalence levels and backend requirements

The staged hierarchy is:

- **E0 semantic validity:** canonical causality, bounds, state definitions,
  reset behavior and finite propagation are respected.
- **E1 numerical equivalence:** declared state/output values are within
  tolerance.
- **E2 event equivalence:** relevant identity, order and timing agree within
  declared tolerance.
- **E3 functional equivalence:** task, prediction or structural outcomes agree.
- **E4 statistical equivalence:** repeated stochastic outcomes agree by
  declared distributions or aggregate metrics.

Required levels are backend- and mode-specific:

| Backend | Required equivalence |
|---|---|
| GPU native | E0; E1 and E2 for reference fixtures; E3 for workloads |
| GPU-FPGA approximation | E0, E1, E2; E3 for workload validation |
| FPGA native | E0, E1, E2 against GPU-FPGA; E3 for workload validation |
| GPU-FPAA approximation | E0 and E3; E1 where modeled; E4 when noise is enabled; E2 only in strict mode |
| Physical FPAA | E0 and E3; E4 for stochastic operation; E1/E2 only where explicitly contracted |
| FPGA+FPAA hybrid | Strict mode: E0-E2; analog mode: E0 and E3, plus E4 when stochastic |

## Equivalence test hierarchy

1. Level 0: canonical analytic Model-B and neuron equations.
2. Level 1: GPU native reference execution.
3. Level 2: GPU FPGA approximation against GPU native.
4. Level 3: actual FPGA against the GPU FPGA approximation.
5. Level 4: GPU FPAA approximation against canonical/reference behavior.
6. Level 5: physical FPAA against the GPU FPAA approximation.
7. Hybrid FPGA+FPAA: a separate full-system comparison against its declared
   digital/analog reference, not an inferred result from component tests.

Each level must preserve causality, bounds, reset behavior and the applicable
A01-A15 checks. Hardware evidence requires versioned traces, declared timing
and numerical tolerances, and explicit unsupported behavior.

## Resource accounting

Logical operation accounting remains separate from backend cost estimates.
Logical measures include event count, edge-transfer count, accumulator update,
spike count and bit-transition proxies. Backend measures may include GPU
operations, FPGA LUT/DSP/BRAM use, analog channels, DAC/ADC use, interconnect,
wall time and measured power. Activity-cost proxies are not joules. Physical
power claims require calibration and must not be substituted into canonical
utility semantics without a separate decision.

## Failure classification

Reports must distinguish:

- **ARCHITECTURE FAILURE:** canonical mechanism or IR contract is insufficient.
- **APPROXIMATION FAILURE:** declared approximation exceeds its contract.
- **BACKEND IMPLEMENTATION FAILURE:** code, RTL or circuit violates its own
  declared backend contract.
- **CALIBRATION FAILURE:** physical mapping is wrong despite valid architecture
  and backend design.
- **HARDWARE LIMIT FAILURE:** the target cannot represent the requested finite
  network or resource contract.

This classification is required before repair or promotion decisions.

## Repository-boundary recommendation

Do not reorganize the repository in this ACP. Future implementation boundaries
should conceptually separate `tpcn/canonical/`, `tpcn/ir/`, `tpcn/runtime/`,
`tpcn/backends/gpu/`, `tpcn/backends/fpga_approx/`,
`tpcn/backends/fpaa_approx/`, `hardware/fpga/` and `hardware/fpaa/`, with
adapters and tests at the boundaries. Existing files remain unchanged until a
separate implementation assignment owns them.

## Future attractor-neuron compatibility

The proposed leaky accumulator and attractor/threshold neuron is recorded as a
future compatible extension only. The IR must be able to carry bounded
accumulator, threshold, hysteresis, reset and attractor-mode parameters without
making them required fields for ACP-0002 N2. The heterogeneous contract also
records the intended work split: every arrival may perform elapsed-time decay,
accumulation and a threshold/attractor test; only a transition may perform
spike emission, downstream fan-out, prediction generation and richer
eligibility/accounting work. This split belongs in ACP-0003 as a portability
requirement and must be finalized by a future neuron ACP. No attractor
transition, threshold rule, spike reset or neuron implementation is authorized
by ACP-0003.

## Implementation staging and authorization boundary

Recommended dependency order:

1. H1: implement the canonical IR/backend interface skeleton under the Luna-18
  dispatch; no approximation or hardware implementation.
2. Keep GPU native as the software reference.
3. Add a GPU FPGA-approximation skeleton with declared quantization and queue
   policies.
4. Add a GPU FPAA-approximation skeleton with declared dynamical/noise models.
5. Review and separately authorize the attractor/event-compression neuron.
6. Implement device-specific backends after contract-level equivalence fixtures.
7. Return edge-parameter learning through its own ACP-0002 governance gate.
8. Consider probationary structural maturation only after local evidence and
   hardware mapping are independently validated.

Luna-18 is authorized for H1 only. H1 must return to Luna-0 before any backend
approximation or hardware work. No production backend, edge learning,
ACP-0002 N3, Luna-13F reopening or Luna-13G authorization follows.

### H1 authorization record

H1 is the smallest first implementation stage: a versioned hardware-neutral
Execution IR, minimal backend identity/capability/equivalence/policy
interfaces, canonical conversion and safe reference reconstruction. H1 must
preserve non-default `w`, `d`, `r`, `tau`, `g` and `lambda`, represent
`SEQUENTIAL_DETERMINISTIC` and future `COINCIDENT_WINDOW` policies without a
physical value, and keep canonical, backend-realization and calibration state
separate. H1 does not implement any approximation or hardware backend.

Luna-18 owns this stage under its agent contract and must return to Luna-0 for
independent review. H1 completion does not authorize H2.

## Required experiments and acceptance criteria

Before backend implementation, define analytic Model-B fixtures, deterministic GPU traces,
fixed-point declarations, queue overflow/backpressure behavior, timestamp and
tie-order rules, FPAA approximation equations, calibration ranges, noise
seeds, reset boundaries and pass/fail tolerances. Compare functional,
numerical, event, structural and statistical outcomes as applicable. Required
checks include no global neural clock, event causality, positive finite delay,
bounded queues/state/topology, equal-time fan-in handling, local prediction and
error chronology, delayed credit identity, deterministic replay where promised,
and capture/telemetry non-interference. Results must be attached to later
implementation handoffs; none are claimed here.

## Unresolved questions

- What exact IR versioning and serialization format should be accepted?
- Which logical state must be reproducible across a backend and which is an
  observable-only internal state?
- What FPGA quantizers, widths, queue overflow and discrete-delay policies are
  appropriate for the first approximation experiment?
- Which continuous-time FPAA model and calibration procedure are credible?
- What calibrated coincidence-window characterization is sufficient for each
  FPAA device and workload?
- Which prediction, eligibility, reward and structural operations belong in a
  hybrid control fabric versus a future analog mapping?
- What physical measurements are available for power and mismatch calibration?
- Which equivalence classes are required for each benchmark and stage?

## Compatibility and migration

ACP-0002 N2 traces, CPU behavior and TPCV-1 remain valid in their declared
scope. TPCV-1 remains downstream-only and is not upgraded into an execution IR
by this ACP. Existing CPU artifacts retain their originating revision and do
not acquire hardware-equivalence claims. A future IR must provide explicit
adapters rather than changing legacy artifacts in place.
